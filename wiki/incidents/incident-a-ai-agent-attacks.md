## 事件經過
- [事實] 資安署 2026-11-11 表示，境外駭客自今年 7 月起運用 AI 代理工具發動網攻，威脅已由政府機關擴展到各類企業與網路平台（S01）。
- [事實] 臺灣已有十餘家企業及網路平台接連受害，累計逾百萬份個資受影響；初步調查近半數攻擊事件與 AI 攻擊有關（S01）。
- [事實] 2026-11-18 行政院引用數發部統計：十餘家企業、機構爆發重大資安事件，外洩個資約 800 萬筆，並函請各部會督促業者依個資法第 12 條及施行細則第 22 條通知當事人（S16）。

## 已確認資訊
- [事實] 官方歸納的弱點有兩類：已知高風險漏洞（舉例 PHP、Node.js、GitLab），以及權限較高、可大量存取資料的 API（S01）。
- [事實] 官方明確提到：企業若應作為而未作為致生損害，可能需負法律賠償責任（S01）。

## 影響範圍
- [事實] 個資外洩；官方並提醒外洩後恐出現利用真實資料的精準詐騙（S01、S16）。

## 為什麼沒有及時發現或防禦
以下為依官方描述所做的推論，非官方結論：
- [推論] 已知漏洞被大規模利用，代表修補速度可能慢於攻擊者自動化掃描的速度。依據：S01 強調「補住漏洞」並要求限期修補；S11 為此訂有 3 天、14 天、60 天的處置期限分級。
- [推論] 高權限 API 讓攻擊者取得入口後可短時間大量取資料，缺乏用量與範圍限制。依據：S01 指出「具有較高權限、可大量存取資料的 API」，並要求「加強系統權限及資料存取管理」。
- [推論] 個資保存範圍過大放大了損害。依據：S01 的「個資最小化」建議（僅收集履約必要欄位、訂保存年限）。

## 如果重新設計，可以如何改善
對應官方建議，並補上本專案的分析：
| 弱點 | 官方建議（S01） | 本 Wiki 補充（推論） |
|---|---|---|
| 已知漏洞未修 | 依警訊做源碼掃描與滲透測試，限期修補 | 以 S11 的風險導向期限分級排序修補；無法修補時用補償性控制 |
| API 權限過高 | 加強系統權限及資料存取管理 | 依 OWASP API Security 的思路做物件層級授權與用量限制（見 concept-api-security） |
| 個資蒐集過多 | 個資最小化、保存年限、去識別化、敏感資料分開存放與加密 | 以資料盤點決定哪些欄位根本不該收 |
| 憑證外洩風險 | 受駭後換發或廢止金鑰、密碼、存取權杖，改用短時效憑證 | 平時即用短時效憑證，縮短被盜用的有效期 |

## 如何應變及降低後續損失
- [事實] 官方「補漏洞」三步：修補前保全系統日誌、全面清查同類系統與內部後台、委由專業鑑識確認無後門（S01）。
- [事實] 官方「快通知」：依個資法第 12 條，查明後以適當方式通知當事人；業者初步掌握範圍即可先行通知，無須等調查完畢；公告應提醒「官方絕不會做的事」（S01）。
- [事實] 通報管道：可通報 TWCERT/CC；涉及個資外洩應依個資法第 12 條、第 27 條及目的事業主管機關訂定的辦法，於法定期限內通報主管機關（S01）。
- [事實] 民眾「自保四原則」：對方說得出訂單細節不代表是真客服；不點不明連結；凡提到操作 ATM 或網銀解除扣款皆為詐騙；常用帳號啟用雙重驗證且不共用密碼（S01）。

### 「72 小時」的性質（重要）
- [事實] 新聞稿中的 72 小時出現在「數發部提出五項應變行動」：重大警訊後 72 小時內完成處置；數位經濟相關企業發現個資外洩應 72 小時內通報主管機關、72 小時內通知當事人、72 小時內找到原因或採取措施；事件後一個月內提出檢討與改善計畫（S01）。
- [事實] 同一份新聞稿引用的法律依據是個資法第 12 條，並轉述其內容為「查明後以適當方式通知當事人」，轉述文字中沒有出現 72 小時的時限（S01）。
- [推論] 因此 72 小時較可能是政策呼籲，而非該條現行文字所定期限。依據：72 小時只出現在「數發部提出五項應變行動」一段。法律條文的現行與未施行版本，見 concept-breach-notification（該頁的條文細節待複核）。


## 官方的進一步說明（S05，2026-10 月報）
- [事實] 月報稱：我國十餘家企業及網路平臺接連受害、累計逾百萬份個資受影響，初步調查近半數事件與 AI 攻擊有關，攻擊者多以已知遭利用漏洞（KEV）進行攻擊（S05）。
- [事實] 月報稱：API 成為駭客攻擊熱區，因為透過 API 取得大量資料相對容易，且部分 API 具有較高權限，一旦受駭容易造成重大衝擊（S05）。
- [事實] 月報的核心論述：AI 改變的是攻擊的速度與成本，本質仍是利用系統弱點與權限管理疏失；攻擊者未必使用全新技術，只要取得有效帳號或掌握可利用的弱點就能入侵（S05）。
- [事實] 月報的建議分兩大項：縮小攻擊面（資產盤點、減少暴露、優先修補、嚴密帳號管理，含 MFA／Passkey、非人類身分盤點），以及做好備份備援（3-2-1、備份環境與正式環境隔離、每季還原演練、備援切換演練）（S05）。
- [事實] 月報的國際對照案例（南韓金融業、日本企業等）不是臺灣事件，且月報註明部分個別事件尚未證實使用 AI 工具（S05）。本 Wiki 不將其當作臺灣事件的證據。
- 時序提醒：月報建立日為 2026-11-16，晚於資安署 11/11 新聞稿；兩者對「十餘家、逾百萬份」的說法一致，沒有出現 800 萬的數字，800 萬出現在 11/18 的行政院新聞（S16）。

## 第二輪補充查證（2026-11-21，非官方來源以標記區分）
- [媒體轉述官方] 資安院院長龔化中於 11/11 說明：許多事件使用名為 ARTEX 的自動化滲透測試工具；該工具原在中國的安全攻防競賽中獲獎、後來開源，遭全球駭客下載並用於攻擊日本、韓國與臺灣；攻擊特徵是繞過前端介面、直攻後端 API 與憑證漏洞（M24）。
- [媒體轉述官方] 數發部說明：受駭個資多為姓名、電話、電子郵件與訂單資料，目前未發現信用卡等付款資訊外洩；大量訂單與聯絡資料流入黑市，已衍生冒名詐騙風險（M24）。
- [媒體轉述官方] 資安署 11/12 表示相關事件影響約 800 萬筆個資，但並非全部都能歸因於 ARTEX（M25）。這說明了「逾百萬份（11/11）」與「約 800 萬筆（11/18，S16）」是不同時點的統計，且後者不全是 ARTEX 事件。
- [媒體轉述官方] 91APP 於 10 月 29 日公布調查結果：駭客利用 ARTEX 自動化攻擊工具，透過第三方系統弱點進入內部網路，非法存取 Commerce Cloud 平台的訂單資料庫；可能受影響資料為姓名、電話、配送地址、電子郵件與訂單紀錄，不含帳號密碼與信用卡等支付資料（M25）。
- [技術研究] FBI 於 11 月 13 日發布警報 FLASH-20261113-001：ARTEX 是由大型語言模型驅動的自主式滲透測試框架，可執行系統偵察、弱點分析與後續入侵，並把資料竊取納入自動化流程（M25 轉述）。TWCERT/CC 轉載 CrowdStrike 對韓國金融業事件的分析，指出攻擊活動涉及多種大型語言模型（M26）。
- [媒體轉述官方] GitLab：資安署 2026-10-02 表示 CVE-2026-85706（CVSS 10.0）為 repository commits API 的路徑遍歷漏洞，特定條件下無須身分驗證即可遠端讀取 GitLab 伺服器上的任意檔案，已遭實際利用並列入 CISA KEV；GitLab 常存放原始碼、系統設定與存取憑證，外洩後可能衍生後續入侵（M27）。
- 仍未取得：受害企業完整名單（除 91APP 自行公布外）、ARTEX 在各案中實際使用的程度。
